Date : 2026-08-29
Périmètre : `index.html`, `projects/artisan.html`, `projects/sma.html`,

Contexte : audit réalisé après le commit `db5cc33` (fondations SEO :

## 1. Résumé exécutif

Le site est un portfolio statique à 5 pages (1 page d'accueil en
sections ancrées + 4 pages projets), sans framework JS, entièrement
rendu côté serveur (c'est-à-dire : le HTML source contient déjà tout le
contenu visible — pas de dépendance au rendu JavaScript pour le contenu
principal). C'est une base technique très favorable au SEO : pas de
risque de rendu/hydratation, pas de contenu caché derrière du JS.

Le commit `db5cc33` a posé des fondations solides et cohérentes :
canonical auto-référencé sur les 5 pages, meta description unique par
page, robots.txt + sitemap.xml cohérents avec les pages réelles du
site, Open Graph et Twitter Cards de base, JSON-LD (Person, WebSite,
BreadcrumbList), preconnect vers les domaines tiers utilisés. Rien de
trompeur n'a été identifié (pas de cloaking, pas de schema ne
correspondant pas au contenu visible, pas de contenu caché).

Les manques restants sont ciblés et peu coûteux à corriger : absence
totale d'image Open Graph/Twitter (impact direct sur le partage social),
titres de pages projets non harmonisés avec la marque, sitemap sans
`lastmod`, quelques incohérences de chemins entre pages. Un point
structurel — la relation entre le domaine `christiandrochon.github.io`
et le domaine custom `christiandrochon.dev` — nécessite une vérification
live que je ne peux pas faire depuis le code seul (section 7).

## 3. Audit détaillé

### 3.1 Technique — crawl, indexation, robots/sitemap, canonical, URLs, rendu, perf

**Preuve directe (lecture de code) :**

- Les 5 URLs listées dans `sitemap.xml` correspondent exactement aux 5
  fichiers HTML présents dans le dépôt. Complétude confirmée par
  comparaison directe. `sitemap.xml` n'utilise pas `<lastmod>`,
  `<changefreq>` ni `<priority>` — non obligatoires, mais `<lastmod>`
  aide le crawler à prioriser les repasses.
- Le fichier `Christian_Drochon_CV_2026.pdf` (racine du dépôt, tracké
  dans git — confirmé, il n'est pas listé dans `.gitignore`) est lié
  depuis `index.html:114` mais **absent du sitemap.xml**. Googlebot peut
  indexer un PDF comme document à part entière et l'afficher dans les
  résultats. Aucune indication dans le code que ce comportement soit
  voulu ou non — voir section Questions ouvertes.
- Le dossier `ue/` (attestations de formation, PDF) est explicitement
  exclu par `.gitignore:26` (`ue/`) — ces fichiers ne sont **pas**
  déployés sur GitHub Pages, donc pas de risque d'indexation
  accidentelle de ces documents. Confirmé, pas un problème.
- Structure d'URL : propre et prévisible (`/projects/<slug>.html`),
  cohérente avec la hiérarchie physique des dossiers. Présence de
  l'extension `.html` dans les URLs — non problématique pour
  l'indexation, juste une préférence esthétique possible (faible
  priorité).
- La page d'accueil est une page unique avec sections ancrées
  (`#about`, `#projects`, `#specialisations`, `#experience`,
  `#contact`). Les fragments d'URL après `#` ne sont pas traités par
  Google comme des URLs indexables distinctes (comportement documenté
  du moteur) : tout le contenu de la page d'accueil est donc indexé
  comme **une seule URL**. Ce n'est pas une anomalie, mais un choix
  d'architecture à assumer consciemment (voir section 6, recommandation
  structurelle L1) — une seule page ne peut cibler qu'un jeu limité
  d'intentions de recherche simultanément.
- Aucune balise `<meta name="robots">` explicite sur aucune page —
  comportement par défaut (index, follow), cohérent avec robots.txt
  qui n'interdit rien. Pas un manque, un choix implicite correct.
- **Point structurel nécessitant vérification live (confiance :
  hypothèse, pas fait)** : le `CNAME` configure `christiandrochon.dev`
  comme domaine custom GitHub Pages. Le canonical déclaré pointe
  systématiquement vers ce domaine, jamais vers
  `christiandrochon.github.io`. C'est une bonne pratique de signal.
  Mais `DECLARED CANONICAL ≠ SELECTED CANONICAL` : si aucune
  redirection serveur (301) n'existe réellement entre
  `christiandrochon.github.io` et `christiandrochon.dev`, les deux
  hôtes peuvent servir un contenu identique et Google peut, dans de
  rares cas, choisir un canonical différent de celui déclaré si les
  signaux ne sont pas jugés assez forts. Je ne peux pas vérifier ce
  comportement HTTP depuis le code seul — voir section 7.

**Perf — signaux observables dans le code (pas de mesure réelle) :**

- 5 requêtes CSS/police potentiellement bloquantes au premier rendu sur
  chaque page : Google Fonts (Inter, 5 graisses), Font Awesome 6.5.1
  (`all.min.css` complet), Bootstrap 5.3.3 complet, plus 2 fichiers CSS
  locaux (`resume-gatsbyjs-colors.css`, `resume-patch.css`) — 3 sur
  `index.html`. Le preconnect atténue le coût de connexion mais
  n'élimine pas la chaîne de requêtes bloquantes elle-même.
- Font Awesome est chargé en intégralité (bundle complet) pour 3 à 4
  icônes réellement utilisées par page (enveloppe, GitHub, LinkedIn,
  globe). **Hypothèse, pas mesurée** : ceci représente probablement un
  poids disproportionné par rapport à l'usage réel — à confirmer par
  une mesure réelle avant d'agir (voir section 7).
- Sur `sma.html`, `marche-financier-risque.html` et
  `vision-ordinateur.html`, le schéma d'architecture est dupliqué 3 fois
  en SVG inline (variantes desktop/tablette/mobile), une seule étant
  affichée selon la largeur d'écran via `display:none` en CSS (confirmé
  légitime, cf. section 2). Cela alourdit le HTML transmis (les 3
  variantes sont téléchargées et parsées même si 2 sont masquées), mais
  reste un contenu vectoriel léger, pas des images bitmap — impact
  probablement mineur, non mesuré.
- Aucune image bitmap (`<img>`) n'est utilisée nulle part sur le site
  (confirmé par recherche exhaustive) — donc aucun problème de poids
  d'image, de `loading="lazy"` manquant ou de dimensions non
  spécifiées. Corollaire : aucun texte alternatif à auditer non plus
  (section 3.2).
- `js/resume.js` est chargé sans `async`/`defer` mais placé en fin de
  `<body>` (`index.html:635`) — équivalent fonctionnel à `defer`, ne
  bloque pas le rendu initial. Correct.

### 3.2 Éditorial / sémantique

- **Titres (`<title>`)** : cohérents et descriptifs sur l'accueil et
  sur `sma.html` / `marche-financier-risque.html`. Deux incohérences
  identifiées :
  - `projects/artisan.html:5` — `<title>Site vitrine artisan</title>`
    ne correspond pas exactement au `<h1>` de la même page
    (`Site vitrine — artisan`, `artisan.html:56`) ; absence de tiret et
    ordre des mots différent.
  - `projects/vision-ordinateur.html:5` — `<title>Multimedia — Vision
    par ordinateur</title>` alors que le `<h1>` de la page est
    `Vision par ordinateur` seul (`vision-ordinateur.html:55`), sans le
    mot « Multimedia » qui n'apparaît nulle part ailleurs dans le
    contenu visible de la page. Risque de dilution du signal
    title↔contenu.
  - Aucune page projet n'inclut le nom « Christian Drochon » ou un
    suffixe de marque cohérent dans son `<title>`, contrairement à
    l'accueil. Pour des recherches de type « [nom] + [projet] », ce
    signal de marque manque sur les pages profondes.
- **Meta descriptions** : uniques par page, pas de duplication,
  correctement alignées avec le contenu réel de chaque page (pas de
  générique copié-collé). Longueur globalement dans la fourchette
  usuelle d'affichage (~150-165 caractères) ; celle d'`artisan.html`
  est la plus longue et présente un risque de troncature à l'affichage
  (impact esthétique en SERP, pas un problème d'indexation).
- **Hiérarchie de headings** : correcte partout (voir section 2).
  Les intitulés `h2` de l'accueil (« À propos », « Projets »,
  « Spécialisations », « Parcours », « Contact ») sont génériques et
  peu porteurs de mots-clés — cohérent avec un usage de navigation
  interne (ancres), mais ce sont aussi les seuls signaux structurels de
  section pour le moteur puisque la page est unique. Pas une erreur,
  mais une opportunité limitée : le contenu réel (riche et
  spécifique — Java/Spring Boot, CQRS/Event Sourcing, OAuth2/OIDC,
  Angular, machine learning) porte les mots-clés dans les paragraphes,
  pas dans les titres de section eux-mêmes.
- **Densité et pertinence du contenu** : chaque page projet a un
  contenu substantiel et spécifique (contexte, objectif, choix
  techniques, stack, compétences démontrées) — pas de contenu fin ou
  dupliqué entre les 4 pages projets. Le texte est écrit pour un
  lecteur humain (recruteur/client potentiel), pas optimisé de façon
  artificielle pour des mots-clés — cohérent avec les critères de
  qualité éditoriale attendus, pas de bourrage de mots-clés détecté.
- **Alt text des images** : sans objet — **aucune balise `<img>`
  n'existe sur le site** (confirmé par recherche exhaustive sur les 5
  pages HTML). Ce n'est ni une conformité ni une violation ; c'est un
  point à garder en tête pour toute image ajoutée à l'avenir (ex. photo
  de profil, capture d'écran de projet, image Open Graph — cf.
  recommandation QW1, qui elle-même n'introduit pas de `<img>` visible
  puisque `og:image`/`twitter:image` sont des métadonnées, pas des
  balises `<img>` rendues).

### 3.3 Structured data / réseaux sociaux

**JSON-LD :**

- `index.html` déclare deux blocs : `Person` (nom, poste, email,
  `sameAs` GitHub/LinkedIn) et `WebSite` (nom, url). Syntaxiquement
  valides à la lecture (accolades/virgules cohérentes). Le type
  `Person` est pertinent pour un site de profil individuel — pas de
  sur-qualification (pas d'`Organization`, pas de faux avis, pas de
  `AggregateRating` inventé).
- Les 4 pages projets déclarent un `BreadcrumbList` à 3 niveaux
  (Accueil → Projets → [nom du projet]), cohérent avec la navigation
  réelle du site.
- **Manques mineurs, non bloquants** : le `Person` n'a pas de propriété
  `url` (pointant vers `https://christiandrochon.dev/`) ni `image`.
  Le `WebSite` n'a pas de `potentialAction` de type `SearchAction` —
  **c'est correct de ne pas l'avoir** puisqu'il n'existe pas de moteur
  de recherche sur le site (ajouter ce schéma sans fonctionnalité
  réelle aurait été une donnée structurée ne correspondant pas au
  contenu, donc refusé si proposé).
- **Écart entre données structurées et UI** (confiance : plausible,
  pas certain) : le `BreadcrumbList` déclaré en JSON-LD sur les pages
  projets n'a pas d'équivalent visuel sur la page — seul un lien
  « ← Retour » existe (`artisan.html:51`, etc.), pas un fil d'Ariane à
  3 niveaux affiché. Les consignes de Google recommandent que les
  données structurées reflètent le contenu visible pour rester
  éligibles aux résultats enrichis (`MARKUP VALIDE ≠ GARANTIE DE
  RÉSULTAT ENRICHI` — même avec un breadcrumb UI ajouté, rien ne
  garantit l'affichage du rich result ; l'absence actuelle n'est pas
  trompeuse, juste incomplète).

**Open Graph / Twitter Cards :**

- **Manque le plus visible et le plus impactant du site** : aucune des
  5 pages ne déclare `og:image` ni `twitter:image`. Confirmé par
  recherche exhaustive (aucune occurrence sur les 5 fichiers HTML).
  Conséquence concrète : tout partage du site sur LinkedIn, X/Twitter,
  Slack, Discord, WhatsApp affichera une carte sans image (ou un
  visuel par défaut selon la plateforme), ce qui réduit le taux de clic
  sur les partages — pertinent pour un portfolio professionnel dont la
  diffusion se fait probablement en grande partie via LinkedIn.
- `twitter:card` est réglé sur `summary` (carte compacte) partout,
  cohérent avec l'absence d'image (une carte `summary_large_image` sans
  image n'aurait pas de sens) — mais devient sous-optimal dès qu'une
  image est ajoutée (voir recommandation QW1).
- `og:site_name` absent partout — optionnel mais recommandé pour la
  cohérence de marque lors des partages.
- `og:locale` absent — mineur, cohérent avec un site mono-langue (pas
  bloquant).

### 3.4 Autorité / liens (limité au code disponible)

Aucune donnée de backlinks externes n'est disponible depuis le code
seul (`BACKLINK COUNT ≠ AUTHORITY`, et de toute façon aucune source de
liens entrants n'est accessible ici) — ce point nécessiterait Search
Console ou un outil tiers, hors périmètre de cet audit (voir section 7).

**Maillage interne (vérifiable depuis le code) :**

- L'accueil lie les 4 pages projets via de vrais `<a href>` HTML
  (`index.html:189, 219, 236, 254`) — crawlable sans JS, pas de lien
  généré dynamiquement qui échapperait au crawler.
- Chaque page projet renvoie vers l'accueil avec une ancre ciblant sa
  propre carte (`../index.html#card-sma`, etc.) — bon maillage
  bidirectionnel, aucune page orpheline.
- **Incohérence de chemins relevée** : `projects/artisan.html:33-34`
  utilise des chemins CSS relatifs (`../css/resume-gatsbyjs-colors.css`)
  alors que les 3 autres pages projets (`sma.html:32-33`,
  `marche-financier-risque.html:32-33`,
  `vision-ordinateur.html:32-33`) utilisent des chemins absolus
  (`/css/resume-gatsbyjs-colors.css`). Ce n'est pas un problème
  d'indexation en soi (les deux fonctionnent), mais une incohérence de
  maintenance qui augmente le risque d'erreur lors d'une future
  réorganisation de dossiers.
- Liens sortants vers GitHub (repos de projets), CNAM (pages de
  formation) et LinkedIn : tous en HTML natif, `rel="noreferrer
  noopener"`, corrects. Pas de « link scheme » ni de lien payant
  dissimulé détecté.

## 4. Constats transverses (risques et hygiène)

- Aucune pratique trompeuse identifiée (cloaking, doorway pages, faux
  avis, contenu fabriqué, données structurées mensongères, réseaux de
  liens artificiels) — le site est propre sur ce plan.
- Le point le plus sensible du site n'est pas dans le HTML lui-même
  mais dans la relation entre les deux domaines (`github.io` vs
  `.dev`) — un point d'infrastructure qui dépend de la configuration
  GitHub Pages / DNS, pas du code source (section 7).
- Le choix d'une page d'accueil unique en sections ancrées est une
  décision d'architecture assumée, pas un défaut technique — mais elle
  limite mécaniquement le nombre d'intentions de recherche distinctes
  que le site peut cibler avec des URLs propres. À garder en tête pour
  une décision future avec `ux`/`po` (section 6, L1), pas une correction
  urgente.

### Quick wins (faible effort, faible risque, réversibles)

**QW1 — Ajouter une image Open Graph / Twitter sur les 5 pages** 🟢
impact plausible, 🟡 bonne pratique standard.
- **Fichiers cibles** : `index.html`, `projects/artisan.html`,
  `projects/sma.html`, `projects/marche-financier-risque.html`,
  `projects/vision-ordinateur.html`.
- **Changement** : créer une image de partage (recommandé : 1200×630px,
  <300 Ko, format JPG ou PNG, ex. `img/og-cover.jpg` ou une image par
  page si souhaité) puis ajouter sur chaque page :
  `<meta property="og:image" content="https://christiandrochon.dev/img/og-cover.jpg">`,
  `<meta property="og:image:width" content="1200">`,
  `<meta property="og:image:height" content="630">`,
  `<meta name="twitter:image" content="https://christiandrochon.dev/img/og-cover.jpg">`,
  et changer `twitter:card` de `summary` à `summary_large_image`.
- **Contrainte** : URL absolue obligatoire (pas de chemin relatif) pour
  que les crawlers sociaux (qui ne résolvent pas toujours le contexte
  de page) trouvent l'image.
- **Critère de vérification (DONE SI)** : les 5 pages contiennent les 5
  balises citées avec une URL absolue qui répond en HTTP 200 ; test
  live obligatoire par l'utilisateur via Facebook Sharing Debugger et
  Twitter Card Validator (nécessite un accès web live, hors de ce que
  je peux vérifier ici).

**QW2 — Ajouter `<lastmod>` au sitemap** 🟢 faisable, 🟡 bénéfice
plausible non garanti.
- **Fichier cible** : `sitemap.xml`.
- **Changement** : ajouter `<lastmod>YYYY-MM-DD</lastmod>` dans chaque
  `<url>`, avec une date dérivée de la date du dernier commit ayant
  modifié le fichier correspondant (`git log -1 --format=%cs <fichier>`).
- **Critère de vérification** : sitemap toujours valide XML (bien
  formé), une `<lastmod>` par `<url>`, dates cohérentes avec
  `git log`.

**QW3 — Harmoniser les titres des pages projets** 🟢 faisable.
- **Fichiers cibles** : `projects/artisan.html`,
  `projects/vision-ordinateur.html` (correction prioritaire — écart
  title/h1 constaté), et par cohérence `projects/sma.html`,
  `projects/marche-financier-risque.html`.
- **Changement** : faire correspondre exactement le texte du `<title>`
  au texte du `<h1>` de la même page, puis ajouter un suffixe de marque
  cohérent (`— Christian Drochon`) sur les 4 pages projets, à
  répercuter identiquement dans `og:title` et `twitter:title`. Exemple
  concret : `artisan.html` → `<title>Site vitrine — artisan —
  Christian Drochon</title>` ; `vision-ordinateur.html` → retirer
  « Multimedia » ou le justifier ailleurs dans le contenu visible, et
  utiliser `<title>Vision par ordinateur — Christian Drochon</title>`.
- **Critère de vérification** : sur les 5 pages, `<title>` et `<h1>`
  contiennent la même chaîne de base ; `og:title`/`twitter:title`
  identiques à `<title>` (moins le suffixe de marque, à la discrétion
  de l'équipe) ; longueur du `<title>` ≤ ~65 caractères.

**QW4 — Ajouter `og:site_name`** 🟢 faisable, 🟡 mineur.
- **Fichiers cibles** : les 5 pages HTML.
- **Changement** : ajouter
  `<meta property="og:site_name" content="Christian Drochon">`.
- **Critère de vérification** : balise présente et identique sur les 5

**QW5 — Harmoniser les chemins CSS d'`artisan.html`** 🟢 faisable,

- **Fichier cible** : `projects/artisan.html` (lignes 33-34).
